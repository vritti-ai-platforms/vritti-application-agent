# vritti-application-agent

An open-source Go agent that runs on a deployment VM (dev on vm1, prod on vm2, or a
customer's own machine), enrolls with **vritti-cloud**, and reconciles the **vritti-core**
stack toward a signed desired-state.

It drives the **Docker Engine API directly** — there is **no `docker-compose.yml`**. The
topology is computed in Go from the deployment's *mode* + *add-ons*, so cloud only sends
config; the agent materializes containers, networks, volumes, and secrets on the box.

## Design principles

- **Cloud is a config + ciphertext relay, never a vault.** Machine secrets (DB passwords,
  JWT/HMAC/COOKIE, Gitea admin) are **generated by the agent on the VM** and never leave.
  Human-entered secrets (R2 keys, external DB creds) reach cloud only as **sealed ciphertext**
  the agent decrypts locally.
- **Two keypairs.**
  - *Deployment key* — cloud holds the private half and **signs** desired-state/commands; the
    agent holds only the public half and **verifies** (this is core's `CLOUD_PUBLIC_KEY`).
  - *Agent key* — generated locally; its public half is registered at enrollment and used to
    **authenticate the agent to cloud** and as the **seal target** for human secrets.
- **Reconciler, not a compose runner.** Every owned object is labeled `vritti.deployment=<id>`;
  a spec hash (`vritti.spec-hash`) detects drift so containers are recreated only when the
  desired spec actually changes. Removed add-ons are pruned.
- **Optional cloud.** vritti-core runs standalone; the agent + cloud connection are additive.

## Flow

| Step | Where | What happens |
|------|-------|--------------|
| i. create deployment | cloud | deployment row created |
| ii. generate signing key | cloud | Ed25519 keypair; **private stored**, **public + join code shown once** = enrollment token |
| iii. start the agent | VM | `VRITTI_ENROLL_TOKEN=<token>` → agent generates its own keys, calls `/agent/enroll` |
| iv. connect (test req/res) | both | cloud returns the deployment public key + a **signed nonce**; agent verifies it → "Connected" |
| v. **mode selection** | cloud→agent | `mode: managed \| external` in desired-state (see below) |
| vi. run | VM | agent reconciles the stack via the Docker API |
| + pgBackRest (premium) | VM | `addOns.pgBackRest` (managed mode only) → backup sidecar |
| + Gitea (add-on) | VM+cloud | agent starts Gitea + bootstraps an admin token → **core-server** creates the git user + PAT and stores them in `vritti_core` |

## Mode selection strategy

| | **managed** (containerized DB) | **external** (bring-your-own) |
|---|---|---|
| Postgres | agent runs `postgres`+pgBackRest (pinned major), bind-mounted `pgdata`; **generates** creds; `EnsureManagedDatabase` creates the `owner`/`app` roles + `gitea` schema | none — operator supplies the connection as the sealed `external_db` secret |
| App `PRIMARY_DB_*` | agent-generated → `postgres:5432` | from the decrypted `external_db` secret |
| Migrations | owner conn against the container | owner conn against the external DB |
| pgBackRest / DbLab | available | disabled (managed DB has its own backups) |

**One Postgres, three schemas** — `core`, `commerce`, `gitea` — all in `vritti_core`, all
covered by one pgBackRest stanza. Only Gitea's repo *files* need a separate backup path.

## Layout

```
cmd/agent/            entrypoint
internal/
  config/             agent boot config (env)
  agentcrypto/        agent keypairs (Ed25519 sign + X25519 seal) + verify/open helpers
  secrets/            agent-generated machine secrets (persisted 0600)
  cloudapi/           wire contract + signed HTTP client
  enroll/             one-time enrollment + nonce handshake
  dockerx/            thin Docker Engine SDK wrapper (run/logs/stats/restart/exec/prune)
  deploy/             spec factory + env renderer + DB-mode branch + reconcile helper
  gitea/              admin-token bootstrap for the Gitea add-on
  agent/              orchestration loop (verify → resolve → migrate → reconcile → report)
```

## Run

```bash
export VRITTI_CLOUD_URL=https://cloud.vrittiai.com
export VRITTI_DEPLOYMENT_ID=<uuid>
export VRITTI_ENROLL_TOKEN=<one-time token from admin>   # only needed on first boot
go run ./cmd/agent
```

The agent needs access to the Docker socket (`/var/run/docker.sock`) and the stack root
(`/opt/vritti-core`, override with `VRITTI_STACK_ROOT`). State lives under
`VRITTI_DATA_DIR` (default `/var/lib/vritti-agent`).
